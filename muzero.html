A self-contained reference - MuZero paper

MuZero, from rules to learned imagination

AlphaGo Zero searched inside a world whose rules were handed to it. MuZero keeps the search, keeps the policy/value learning loop, but removes the rulebook. It learns a private hidden world that only has to answer three questions: what reward comes next, what action looks promising, and how good is this state?

How to read this. This is not a survey of all Alpha systems. It is one paper, end to end. The toy world is tiny on purpose: if MuZero is clear there, the Atari/Go/chess/shogi version is the same machine with bigger networks, more simulations, and much more compute.

1The crutch MuZero removes

AlphaGo Zero and AlphaZero had a clean split:

simulator applies the rules   +   neural net scores positions   +   MCTS improves the move

The simulator was not a small detail. It was doing three jobs inside search:

job done by rules in AlphaZeroexamplewhy it matters
state transitionif I play knight to f3, what board results?search can move from node to node
legal action maskwhich moves are legal from this node?search does not waste time on impossible moves
terminal detectionis this checkmate, resignation, or game end?search can use true terminal value

MuZero removes those three rule-based services from the tree and replaces them with a learned model. The model is not asked to predict the next pixel frame. It is not asked to reconstruct the true hidden state of the game. It is asked to support planning.

?check yourselfIf MuZero is still using MCTS, is it secretly just AlphaZero with a worse simulator?

No. That is the tempting but wrong compression. AlphaZero's simulator is external and exact. MuZero's model is internal and optimized for planning targets. It does not have to be a faithful simulator of the world. It has to be value-equivalent enough: actions that lead to good returns should look good inside the model, and actions that lead to bad returns should look bad.

So the right sentence is: MuZero keeps AlphaZero's search-based policy improvement, but replaces exact rules with a learned, planning-shaped latent dynamics model.

2The three functions: h, g, f

MuZero's model is three functions wired together. The paper uses these names:

s0 = h(observation history)
rk, sk = g(sk-1, ak)
pk, vk = f(sk)

The functions have separate jobs:

piecejobplain English
h representationturn real observations into the first hidden state"Compress what I have seen into the private state search will start from."
g dynamicstake a hidden state plus a hypothetical action, output reward and next hidden state"Imagine one action forward."
f predictionturn a hidden state into policy and value"From here, what moves look good, and how good is this?"
?you hit this earlyWhich part of MuZero sees real observations: h, g, or f?

Only h sees real observations. The representation function gets the observation history and makes s0. After that, search lives in hidden states. g sees hidden state plus action; f sees hidden state. Neither one needs pixels or a board.

This is why MuZero can search many imagined futures without calling the environment. It pays for one representation at the root, then repeatedly applies a smaller recurrent model inside the tree.

3The hidden state has no obligation to look real

This is the line that separates MuZero from a normal world model. A normal model-based RL system often tries to predict the next observation, or reconstruct the real state. MuZero does not.

MuZero's hidden state can mean whatever helps predict reward, policy, and value. It can cache threats, remember a key was picked up, encode a tactical pattern, or store something no human would name. If it supports planning, it is allowed.

That is both powerful and unsettling. It means you cannot inspect s and expect "this cell is a wall, this pixel is a door." It may not be a map. It may be a plan-shaped compression.

?core misconceptionIf the hidden state is not forced to reconstruct the observation, how can it avoid hallucinating nonsense?

Because the training targets are not "look realistic." The targets are: predict the actual reward, predict the search policy, and predict the return. If the hidden state hallucinates in a way that hurts those targets, the loss punishes it. If the hidden state ignores irrelevant visual detail and improves those targets, the loss rewards it.

So the hidden state is not unconstrained. It is constrained by planning usefulness, not by pixel fidelity.

4A tiny world with a key, a coin, and a locked door

We need a world small enough to search by hand, but MuZero-shaped enough to show the new idea. Here is the entire real environment. MuZero is not given these rules; they are just our hidden answer key.

real stateactionnext real staterewardobservation
start, no keycointerminal+1coin collected
start, no keydoorterminal-1locked door hurts
start, no keykeyhas key0same hallway screen
has keydoorterminal+5door opens
has keycointerminal+1coin collected

The trap: coin gives immediate reward +1. key gives no reward now, but unlocks +5 next. With discount gamma = 0.9, the two-step key plan is worth:

0 + 0.9 * 5 = 4.5

So the optimal first action is key, even though it looks worse immediately.

?importantIf the screen after key looks almost the same, where can MuZero store "I have the key"?

In the hidden state. At the real root, h can encode observation history and action history. Inside search, g(s0, key) can produce a new hidden state s_key that carries "door now works." It does not need a visible key icon. It only needs future predictions to change: door should now predict reward +5 and high value.

5One imagined step: the dynamics function

At the root, suppose the current network is still naive. Its raw policy likes the immediate coin:

action at startpolicy prior pmodel's one-step prediction from gprediction from f after that
coin0.55r = +1, hidden state s_coinv = 0.0
door0.25r = -1, hidden state s_lockedv = 0.0
key0.20r = 0, hidden state s_keyv = 4.4

That last line is the whole trick. The reward for key is zero, but the next hidden state is valuable because the model has learned that from s_key, the door can produce +5.

return(key, one-step lookahead) = r_key + gamma * v(s_key) = 0 + 0.9 * 4.4 = 3.96
?do not miss thisDoes v(s_key)=4.4 mean the agent has already opened the door in the real environment?

No. It is an imagined hidden state inside the search tree. The real environment has not moved. The model is saying: "If I were in the state produced by taking key, the expected discounted return from there would be about 4.4." Only after search chooses a real action does the environment step.

6Search inside the learned model

MuZero's search is still MCTS-like, but every edge stores more than AlphaGo Zero's edge did. In the paper, each edge stores:

{ N(s,a), Q(s,a), P(s,a), R(s,a), S(s,a) }
symbolmeaningwhere it comes from
Nvisit countsearch bookkeeping
Qmean backed-up returnaverage of returns through that edge
Pprior policyprediction function f
Rpredicted immediate reward for this edgedynamics function g
Spredicted next hidden state for this edgedynamics function g

The backup is the main change from AlphaGo Zero. AlphaGo Zero mostly backed up a value with sign flips because board games had terminal rewards. MuZero can have intermediate rewards, so the backed-up number is a discounted reward chain plus a leaf value:

G = r1 + gamma*r2 + gamma^2*r3 + ... + gamma^L*v_leaf
?new MuZero thingIn AlphaGo Zero, a simulation backed up a leaf value. In MuZero, what exactly gets backed up?

A cumulative discounted return. If the imagined path saw rewards 0, then +5, and the leaf value was 0, the root edge receives:

0 + 0.9*5 + 0.9^2*0 = 4.5

So MuZero's backup carries both predicted rewards on the path and the predicted value at the leaf. That reward head is not decoration; it is what lets MuZero handle Atari-style domains where points happen along the way.

7A full MuZero search with numbers

Now run a tiny search at the start screen. The raw policy prior likes coin, but the learned model knows the key can lead to the door.

Here is the same search as a table, simulation by simulation. We are simplifying the selection formula, but keeping the MuZero-specific backup exactly in spirit: predicted rewards plus discounted leaf value.

simpath imagined by searchreturn backed to rooteffect
1coin+1 + 0.9*0 = +1.00coin gets the first easy win
2door-1 + 0.9*0 = -1.00locked door is punished
3key0 + 0.9*4.4 = +3.96search notices the latent key state is valuable
4key -> door0 + 0.9*5 = +4.50search confirms the real plan inside the model
5-9mostly key brancharound +4.5visits pile onto key

After nine simulations:

pi(key)=6/9=0.67,   pi(coin)=2/9=0.22,   pi(door)=1/9=0.11

The network's raw policy said coin. The search policy says key. That disagreement is the learning signal.

?search vs modelIf p at the root liked coin, why did search end up choosing key?

Because p only biases which branches get tried. Once a branch is tried, Q starts carrying return information. The key branch gets a low immediate reward but a high future value, then a direct imagined +5 when search expands key -> door. Its Q becomes much larger than coin's +1, so visits move there.

?the MuZero-only partDuring the path key -> door, did search ask the real environment whether the door opens?

No. It asked the learned dynamics function. Search calls g(s0, key), then g(s_key, door). The real environment is not touched until after search finishes and one action is selected at the root.

That is why model error matters. If g falsely believes the door opens without a key, search can be fooled. The only cure is training against real rewards and future search targets.

8Acting: only now does the real environment move

Search produced pi. Acting is simple: sample from pi during training, or take the most visited action during evaluation. Suppose we play key.

REAL STEP 1start screensearch chooses the delayed plan
front end
start -> after key environment returns reward u1 = 0
back end

Only this step changes the real world. All previous key-door reasoning was imagined. The replay buffer records the observation, the search policy at the root, the action key, and reward 0.

At the next real timestep, h builds a fresh root hidden state from the new observation history. The screen is similar, but the history includes that key was taken, so the hidden state can be different.

REAL STEP 2has keynow door is immediately best
front end
has key -> open environment returns reward u2 = +5
back end

The second search is short: the door branch predicts immediate reward +5, so pi(door) becomes nearly all the mass. The episode ends with total discounted return 0 + 0.9*5 = 4.5 from the start.

?online/offline splitWhen did learning happen in those two real steps?

Not during the steps themselves. Acting generates data. The model weights are fixed while search and environment interaction happen. Learning happens later when trajectories are sampled from replay and the network is trained to match rewards, returns, and search policies.

9The episode becomes training data

The full real episode is tiny:

start --key, reward 0--> has_key --door, reward +5--> terminal

Each real timestep has a search policy pi_t, a real action, and a real reward. The value target is a return. For this toy with gamma=0.9:

Three different targets train three different parts of the prediction:

targetteachessource of truth
pipolicy head: imitate the improved searchMCTS using the current model
zvalue head: predict return from hereactual rewards plus bootstrap/search value

?targetsWhy does MuZero need a reward target if it already has a value target?

Because value compresses the future into one number, while reward tells the dynamics model what happens on each transition. In Atari, rewards happen along the way: points for eating a pellet, losing a life, collecting an item. Search needs those transition rewards to compare paths before the final outcome.

In board games with no intermediate rewards, the paper omits the reward prediction loss. In Atari-like domains, the reward head is essential.

10Training by unrolling through real actions

Training samples a real trajectory from replay, picks a starting time, then unrolls the model for K hypothetical steps using the real actions that actually happened. In the paper's experiments, K=5.

The loss for one sampled start is the sum over unrolled steps:

loss = sum_k [ reward_loss(u_t+k, r^k) + value_loss(z_t+k, v^k) + policy_loss(pi_t+k, p^k) ] + regularization
?easy to mix upDuring training, does MuZero unroll through the actions search wanted to try, or the actions that actually happened?

The actions that actually happened in the sampled trajectory. Search may have imagined many branches, but the replay trajectory contains one real action sequence. Training aligns g's imagined transitions along that real sequence with the observed rewards and future search policies.

This is why the model is grounded. It cannot only train on fantasy branches. The reward targets come from the environment's actual response to chosen actions.

?value targetFor Atari-style rewards, why is the value target not just final win/loss?

Because Atari has long episodes and intermediate rewards. The paper uses an n-step return: add the next real rewards for a while, then bootstrap from a later search value.

z_t = u_{t+1} + gamma*u_{t+2} + ... + gamma^n * search_value_{t+n}

For board games, the final outcome works because the main reward is at the end. For Atari, waiting for the full final episode target would be too delayed and too noisy.

11What MuZero does not know inside the tree

The appendix comparison to AlphaZero contains three surprising details that are easy to miss.

inside the search treeAlphaZeroMuZero
state transitionexact simulator applies rulesg predicts next hidden state
legal actionssimulator masks legal actions at every nodelegal actions masked at root only; inside tree the model learns from trajectories
terminal nodessimulator detects terminal and supplies true terminal valueno special terminal treatment inside tree; value is predicted by network

That means MuZero can search past an imagined terminal state. Training handles this by treating terminals as absorbing: after the end, the model should keep predicting consistent values.

?strange but trueIf MuZero does not detect terminals inside the tree, how does it know a game is over?

The real environment tells it when acting, but inside the search tree MuZero does not call the environment. It relies on predicted reward and value. If the environment ended in replay, training teaches the post-terminal hidden states to be absorbing, so continuing to unroll should not create fake extra rewards.

This is one of the prices of removing the rulebook. MuZero gains generality, but now the model must learn things the simulator used to give for free.

In three sentences. MuZero takes the AlphaZero loop and removes the rule simulator from inside search: the root is encoded by h, imagined transitions are produced by g, and policy/value estimates come from f. Search backs up predicted rewards plus discounted leaf values, producing a better policy pi; only after search chooses an action does the real environment move and reveal the actual reward. Training then unrolls the model along real replay actions and pulls p -> pi, v -> z, and r -> u, letting the hidden state become whatever private language makes planning accurate.
