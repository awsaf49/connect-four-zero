Blog series draft - successors with minimal overlap

Alpha systems after AlphaGo Zero

A set of blog-style notes for the papers you downloaded. Each chapter is built around one new idea, so the posts do not all say "policy, value, MCTS, repeat" in slightly different clothes.

Series rule: each post gets exactly one central novelty, one toy mental model, and one design lesson for a useful visual self-play project.

01 - MuZero

The model does not learn the world. It learns the part of the world needed for planning.

AlphaZero searches with a real simulator. MuZero removes that crutch: it learns a latent dynamics model and plans inside that model.

New idea: do not predict pixels or legal-game state. Predict only reward, value, and policy-relevant future.

Toy mental model

You are navigating a building during a fire drill. You do not need a photorealistic model of the wallpaper. You need: if I take this hallway, do I get closer to an exit, blocked, or trapped?

Design lesson for us

For a visual self-play project, the learned model should not reconstruct images. It should predict the future judge signal, possible next visual states, and which interventions are promising.

Blog hook

Title idea: "MuZero: the system that learned to dream just enough." The surprise is not that it builds a world model. The surprise is that it refuses to build more world than planning requires.

02 - Gumbel MuZero

When search is expensive, do not search everything. Run a tournament.

Classic MCTS needs many simulations before visit counts become meaningful. Gumbel MuZero asks a sharper question: with a small budget, can planning still produce a policy improvement?

New idea: use Gumbel top-k sampling and sequential halving to allocate a tiny search budget like a knockout bracket.

Toy mental model

You have 16 logo designs but only 20 minutes of user testing. Do not test all 16 equally. Pick a diverse shortlist, do quick tests, cut half, test survivors deeper.

Design lesson for us

If our visual task has lots of possible edits, questions, or puzzle moves, a tournament-style planner can make the demo feel smart without needing thousands of simulations per step.

Do not overuse this post: it should not re-explain MuZero. It should be about the search budget problem: how to make a small number of simulations count.
03 - Sampled MuZero

Some worlds have too many actions. So the action space must be sampled, not enumerated.

Board games have a manageable legal move list. Real design problems do not. Sampled MuZero keeps the MuZero spirit while planning over only a proposed subset of actions.

New idea: a policy can propose candidate actions, and search can improve over that sampled set without listing every possible action.

Toy mental model

A city planner cannot evaluate every possible traffic-light schedule. First generate 40 plausible schedules, then search among those and mutate the best.

Design lesson for us

For visual puzzles, actions might be continuous: move a shape, ask a question, alter a scene, add an occluder. The system needs an action sampler before it needs a giant search tree.

Good use case for our project

Teacher-agent puzzle generation. The teacher can sample candidate puzzle edits, the solver tries them, and search keeps edits that create useful difficulty rather than random mess.

04 - EfficientZero

The question changes from "can it learn?" to "can it learn before the compute bill eats the demo?"

MuZero is beautiful but hungry. EfficientZero asks how to keep the model-based planning loop while squeezing more learning out of each interaction.

New idea: sample efficiency is an algorithmic feature, not just an engineering detail.

Toy mental model

You filmed only two hours of a robot moving boxes. A wasteful learner watches once. An efficient learner keeps relabeling old moments with its newer, smarter judgment.

Design lesson for us

If we build a visual self-play demo, we cannot rely on millions of expensive episodes. We need cached scenes, relabeled targets, contrastive visual learning, and lightweight search.

Best blog angle: make this the "how to make the surprise affordable" post. It is less glamorous than MuZero, but probably more important for something we can actually run.
05 - AlphaTensor

Not every game has two players. Some games are just unfinished mathematics.

AlphaTensor takes the AlphaZero recipe out of board games and into algorithm discovery. The player makes moves that reduce a tensor until a matrix multiplication algorithm appears.

New idea: discovery can be framed as a single-player game with a verifiable final object.

Toy mental model

Imagine a puzzle where every move subtracts a simple transparent sheet from a complicated image. Win by explaining the image with the fewest sheets.

Design lesson for us

This is the strongest precedent for "not Go, still useful." If our visual system can produce a final artifact that is automatically checkable, self-play becomes discovery rather than entertainment.

Project directions inspired by AlphaTensor
  • Discover short visual programs that generate a target diagram.
  • Discover compact rule sets for puzzle families.
  • Discover scene decompositions: explain an image with a small number of geometric operations.
06 - AlphaDev

Programs can be treated as trajectories. The reward is whether they run correctly and faster.

AlphaDev searches through low-level program instructions to discover small algorithms, such as sorting routines, that beat human-written baselines.

New idea: the environment can be a compiler, a CPU, and a test suite. Correctness is the referee.

Toy mental model

Instead of writing a recipe, the agent places one kitchen action at a time. The judge eats the final dish and times the cooking process.

Design lesson for us

For visual reasoning, we can search over visual programs: crop, group, count, rotate, compare. Surprise comes when the agent discovers a weird but valid procedure humans would not script.

Risk for our project: if the verifier is weak, the system will exploit it. AlphaDev works because tests and performance measurement are hard external feedback.
07 - AlphaProof

Reasoning self-play needs a referee that cannot be charmed.

AlphaProof is not about board games. It uses reinforcement learning in a formal environment, where proposed proof steps can be checked by Lean.

New idea: the verifier is the source of truth. That is how self-generated reasoning data avoids becoming self-delusion.

Toy mental model

A student can invent unlimited practice problems, but the answer key must be exact. Otherwise the student learns to persuade itself.

Design lesson for us

Our visual system needs a verifier: rendered scene metadata, programmatic object relations, physics constraints, or a simulator. A learned judge alone is dangerous unless calibrated against something external.

Why this matters for visual self-play

If a VLM asks questions and another VLM answers, that is not enough. The third thing, the verifier, is the whole load-bearing wall. It is the difference between AlphaProof-style improvement and synthetic-data collapse.

08 - AlphaFold

AlphaFold is not an AlphaZero successor. It is a lesson in visual surprise.

AlphaFold does not use self-play or MCTS in the AlphaZero sense. But it is extremely relevant to the emotional target: a dull input becomes a hidden structure you can see.

New idea: the most powerful demo may not be winning a game. It may be revealing structure that was invisible in the input.

Toy mental model

A long string is a compressed sculpture. The model learns how local and long-range constraints force the sculpture into shape.

Design lesson for us

Maybe our project should not just show agents winning. It should show hidden visual order emerging: folds, layouts, routes, decompositions, curricula, or puzzle families.

How to use this post: be honest that AlphaFold is not in the self-play/MCTS lineage. Its value is inspiration for the artifact: a visible structure no one expected.
